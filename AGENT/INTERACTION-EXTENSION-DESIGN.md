## 一、A-007 预算域解析/推荐 + 反馈联动

### 用场景说

你把"住院预算"拖入神经外科的 budget 槽后，系统自动分析当前预算状态并弹出推荐——
比如：①"该预算已分配给 3 个单元，其中神经外科占 30%，还有 70% 可分配"；②"该单元
已有另一笔预算（门诊预算），两笔合计 130 万，超出该单元历史标准 100 万，建议核查"；
③"该预算已全部占用，无剩余可分配"。

**推荐类型设计**（需要你裁定的核心——这些是我建议的初式类型，你增删）：
- **allocation-status**：预算拖入后展示该预算当前分配状态（已分配/未分配/已耗尽）；
- **over-allocation**：同一单元的预算合计超限提示（occupied > total 时的 D-024 既有语义展示）；
- **allocated-but-idle**：已分配未占用提示（D-025 既有语义展示）。

**关键边界**：这三类都是**预算服务（budgetService）既有派生状态**的展示推荐——
不发明新的预算语义，只是把 Q-05 封板的派生规则接入推荐面板。推荐本身不改任何事实
（D-130 同理：推荐 ≠ 事实），你确认后也**不执行任何预算动作**（预算没有 confirm
链——因为推荐的只是"信息展示"而非"操作建议"）。

**联动**：预算关系变化（解除/移动/撤回）时，相关推荐按 D-151 同款规则失效；
未来如果预算推荐含"操作建议"（如"建议解除 X 占用以腾出空间"），再走 UserDecision
确认链——V1 先只做信息展示类。

**待你裁定**：①推荐类型清单（上面 3 类是否合适，有无增删）；②预算推荐出现在
"推荐面板"（与工作量推荐混合展示）还是独立分区（推荐面板按 kind 分组显示）？

## 二、A-009 单元卡组织结构 + 按"科室对应表"拆分

### 第一半：单元拖入单元槽 = 组织结构（封板语义，无需裁定）

Q-04 封板了 structure 关系语义（D-015：V1 Unit Slot 只接受 UnitCard）。实施 =
单元卡从 Deck 拖入画布上某单元卡的 unit 槽 → 建立 structure 从属关系。交互与
workload/budget 同款：芯片显示、拖出解除、槽间移动。**B 类可自主——无需设计稿**，
本报告后我直接实施。

### 第二半：按"科室对应表"拆分（新语义，需要你裁定）

**场景**：护理组（单元卡）拖入神经内科单元下 → 系统识别"护理组下有按科室的
子分组"（对应表数据）→ 提出"将拆分为：神经内科护理组"→ 你确认后创建
"神经内科护理组"卡并挂入神经内科的单元槽。

**设计提案（推荐-确认流，与 A-003 拆分复用同款精神）**：
1. **触发**：单元卡拖入另一单元的 unit 槽 → 系统查询"科室对应表"——如果该单元
   按当前目标单元的科室存在可细分的分组（如护理组 × 神经内科 = 神经内科护理组）；
2. **推荐**（不是静默创建）：弹推荐"将拆分出：神经内科护理组——确认创建并挂入？"
   推荐面板显示（与工作量拆分推荐同面板）；
3. **确认**：你点确认 → 创建新 UnitCard（名称 = 对应表映射结果，如"神经内科护理组"）
   + 建立 structure 关系（新卡 → 目标单元）+ 挂入单元槽显示；
4. **不确认**：点暂不采用 → 不创建（推荐关闭）。

**核心待裁**："科室对应表"的正式模型——
- 它是数据准备阶段的一部分（数据上传时定义"护理组"这个分类下按科室可细分为哪些组），还是
- 系统内置的组织模板（每个 unitKind 有一套标准拆分规则）？

**我的推荐**：数据准备层定义（Phase 2 范畴，但可以先做接口 + 演示数据），因为你们
裁定的"工作起点是数据上传"（历史 0409）+ 医院各自的对应表不同（历史 L3386 你提过
人工智能辅助生成对应表的愿景）。演示阶段可以像 A-005 医生维度行一样：在演示链里
补几行"护理组按科室细分"的映射数据，让整个流程可以走通。

## 三、A-010 画布聚焦模式 + 双击聚焦 + 卡牌归位

### 历史锚定（已核实）

- **三态模式**（历史 L3500-3530，用户已赞同）：聚焦模式 = 默认（当前对象+一级关联）/
  扩展模式（上下多级+引用）/ 全景模式（整个结构）；
- **DEC-006**（历史 L25638）："牌盒点击 ≠ Canvas Focus；拖入 Canvas = Focus"——
  **注意**：本轮用户裁定说的是"**双击**牌盒中的卡/槽内的卡/虚影卡 → 设为聚焦"。
  两者的精确对齐 = **单击查看/选中，双击聚焦**（单击不改变画布焦点，双击才改变）。
  这是对 DEC-006 的重锚定（从"点击不聚焦"演进到"单击不聚焦/双击聚焦"），不是推翻
  ——请你在批复时确认这一解读；
- **一棵树**（历史 L6120）："虚影代表路径，实体代表当前工作对象"——聚焦时画布
  只呈现当前核心的卡牌树（上下级用虚影方式呈现路径），不会出现两组独立树。

### 设计要点

1. **聚焦触发**：双击（Deck 卡 / 槽内卡 / 虚影关联卡）→ canvasStore.focusCardId
   更新 → 画布重渲染为聚焦模式；
2. **聚焦渲染**：当前聚焦卡（画布中心）+ 一级关联卡（直接上下级/槽内关联）；
   非关联零散卡自动回 Deck（A-008 互补：Deck 过滤 = "已关联的卡不显示"，
   聚焦归位 = "画布上不相关联的卡回 Deck"）；
3. **归位规则**：聚焦变化时，画布上不在新聚焦卡关联范围内的卡 → placement 移除
   → 该卡回 Deck 显示（因为回 Deck 后该卡要么无关联 → Deck 直接显示，要么有
   关联 → 不显示但也不再占画布空间）；
4. **模式切换**：聚焦/扩展/全景三态——V1 先做聚焦模式（默认），扩展/全景归
   正式 UI 阶段（涉及视觉设计）；
5. **双击 vs 拖动冲突**：单元卡现在可拖动重定位（U-UI-10）——双击与拖动不冲突
   （双击 = 无拖动的快速连击），浏览器原生区分。

### 待你裁定

1. **DEC-006 重锚定**：单击查看/双击聚焦——确认这个解读？
2. **归位 = 物理移除画布 placement**：归位后该卡的画布位置信息消失（下次聚焦
   该卡时重新布局）——还是保留 placement 只隐藏（下次聚焦还原位置）？
   我推荐保留（历史 L6123 Focus Trail 精神——位置记忆），但"零散卡回 Deck"
   的视觉语义是"不在画布上"——保留 placement 只影响下次回来时的位置体验，纯
   UI 状态，不涉业务事实。推荐保留，请确认。
3. **虚影卡**（上下级路径提示）：V1 简化为"仅一级关联卡实际显示，不渲染虚影"，
   虚影归正式 UI 阶段（视觉设计）——可以吗？
