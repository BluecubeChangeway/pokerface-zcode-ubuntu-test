### A-002｜移动 / 解除关系操作语义（U-02，D-151 剩余②） `[用户裁定 + 工程假设]` 2026-10-21

**用户裁定（原话要点）**："衍生出的交互卡片与手工卡片地位相同。当把一张卡从一个单元的'口袋'拖到另一个时，就相当于这张卡片**解除了之前的关系又新建了关系**。"——与 D-151 正文自带示例（"用户将 A 从 B 移到 C：A→B 发生有效关系变化 → 旧当前反馈失效（不提示）→ 自动 Resolution(A, C)"）完全一致；U-02"操作语义待产品裁定"就此关闭。

**工程落地（服务层，UI 接线归 UI 产品化阶段）**：
1. `moveWorkloadCardAssignment(dataService, workloadCardId, fromUnitId, toUnitId)`：
   - 校验：卡与双端 Unit 存活且类型正确（D-154：revoked = 业务不存在，静默 ignored）；
   - 同单元移动（from === to）→ no-op；
   - 解除：将 active (fromUnit → 卡) 软删除（active=false，同 ID upsert，保留审计行——与撤回的关系软删一致）；
   - 新建：目标端按 P2-1 业务键幂等（已有 active 同键 → reused；无 → 经 relationService.createRelation 端点校验新建，metadata.origin="move" 不参与业务键）；
   - 解除与新建经 `ActionSubmissionService.submitMoveAssignRelation` 一批持久化（D-141：唯一 save\* 边界；重试幂等收敛）；
   - 持久化成功后：**配对级失效**——移除 kind=resolution 且 status=recommended、锚定为 (卡, fromUnit) 的旧反馈（D-151：关系已解除不提示、不保留当前反馈）；accepted/ignored/dismissed 历史与非 resolution kind 不触碰；
   - 然后对 (卡, toUnit) 自动重新 Resolution（复用 resolutionTrigger，D-142 稳定 ID）。
2. **微决策（[假设]，五项随行）**：(a) from 端无 active 关系时"解除"为 no-op、仍执行新建（视为纯指派）；(b) to 端已有 active 同键关系时幂等复用、旧关系仍解除（卡最终只挂目标端）；(c) 无效参数静默 ignored（对齐 AGENTS §20 拖拽语义）。
3. **边界**：移动不触碰统计事实（WorkloadResult/WorkloadSplit 不变）；不做"解除关系"独立入口（解除 = 移动到"无"，属 UI 产品化形态，届时另议）。

**风险**：批量持久化在 Mock 内存环境为单调用；生产适配器落地时需事务/幂等保障（WK §16.5 Deferred 原则不变）。重试收敛已由幂等设计覆盖（测试验证）。

**验证**：moveRelation.test.ts（2026-10-21，与 A-002 同批实施，结果见 AGENT_STATUS §2.5）。

### A-004｜存储演进路线（R4，用户裁定方向 + 工程优化） `[用户裁定方向 + 工程优化建议]` 2026-10-21

**用户裁定（原话要点）**：现阶段优先实现**本地存储** → 未来**服务器端备份与恢复**（不用实时备份，**闲时备份**即可）→ 两者成熟后**多人协作**（主用户授权子用户，子用户局域网内直接读写主用户数据，主用户审核确认，云端备份）→ 再往后**互联网异地协同**。要求优化路线、原则 = 减少重复开发与过度重建。

**工程优化方案（消化后）**：
1. **全部阶段共用 DataService 适配器边界**——现有接口即持久化抽象层，各阶段 = 新适配器实现，不重建领域层（零重复开发的结构保证）；
2. **阶段 1（R4a）本地存储 = 指定文件夹 + 轻量本地服务**（用户 2026-10-22 修订：**不采用浏览器内存储**——本项目数据具"工程资源"特质，应存于用户指定或系统指定的特定文件夹；未来云端备份亦从该文件夹同步；阶段 3/4 时再议本地存储作为缓存还是主数据源）：实现形态 = 零依赖 Node 本地服务（`local-server/`）拥有并管理该文件夹（DATA_DIR 可配置，默认 `./poker-face-data/`，JSON 文件分集合存储、原子写入、人可检视），前端经 HTTP 与之通信（`LocalFolderDataService` 实现 DataService 接口）；D-143/D-148 迁移约束（真实持久化前的 ID 切换已按时序完成，无遗留）；
3. **阶段 2（R4b）闲时备份 = 导出/快照文件 + 可选服务端推送**：备份 = 全量状态序列化（复用 DataService 读接口），闲时触发（用户手动/定时），不建实时同步（避免过度工程）；
4. **阶段 3（R4c）局域网协同 = 本地服务 + 授权模型**：届时引入轻量服务进程（主用户机），子用户经授权读写——**设计前提**：领域层不感知多用户（全部经 DataService 边界），协作冲突处理届时按"主用户审核确认"设计（与现有幂等/业务键机制衔接）；
5. **阶段 4（R4d）异地协同 = 阶段 3 的网络延伸**，不另起架构；
6. **明确不提前做**：实时同步引擎、完整权限系统（AGENTS §26 边界）、操作转换（OT/CRDT）——阶段 3 裁决前不引入。
**实施顺序**：R4a 即可开工（技术选型属工程师职责，无业务语义变更）；R4b 随后；R4c/R4d 届时出设计呈报。

## A-001 原始假设记录（2026-10-21 首版，方案 A——已被上方方案 B 裁定取代，保留为审计轨迹）

**① 假设内容**：撤回提交成功后（A① 失效之后），自动重新 Resolution 的配对范围按撤回意图分流：
- **层撤回**（revokeSplitLayer）：对**父卡（parentWorkloadCardId）的全部 active workload_assign 配对**（父卡, 目标 Unit）自动重新执行 Resolution（复用 resolutionTrigger，D-142 稳定 ID / re-offer 语义，不新增推荐通道）；
- **全路径撤回**（revokeDerivedPath / revokeDerivedPathAsPreviewed）：**不自动重推任何配对**。
- 双侧均不自动执行任何业务动作（D-151："自动"只表示自动分析和推荐）。

**② 选择理由**：
- D-151 裁定方向："关系变化即失效并自动重新 Resolution"。层撤回的业务意图是"这一层拆分错了、想重新来"（历史 1240 场景）——父卡与目标 Unit 的 assign 关系仍有效、其上下文（拆分事实）刚被清除，自动重推正好承接"重新来"的意图，消除现状"撤回后需手动再次拖入同一张卡"的多余操作（U-01 记录的差距）。
- 全路径撤回的意图是"从头到尾全错了"（历史"我把妇产科出院人次给了骨科"）——原地立即重推同类建议与该意图相悖；用户把卡拖到正确 Unit 时 D-150 自然触发 Resolution。
- 两撤回分支语义互斥（D-153），配对范围按意图分流与之一致。retained 子卡自身的 assign 关系未变化（D-151 触发条件是"关系变化"），不误推。

**③ 可选替代方案**：
1. 全路径撤回也对入口卡配对重推——否：与"全错了"意图相悖（已验证：全路径影响集不软删入口卡自身 assign，该配对仍 active，此为真实行为选择而非被动物极）。
2. 层撤回同时对 retained 子卡的配对重推——否（首版判断）：retained 子卡自身关系未变化——**该判断已被用户 2026-10-21 方案 B 裁定推翻，见上方现行版**。
3. 不做自动重推、保留手动再拖——否：即 U-01 标记的未完成项本身，且 D-151 已裁定"自动重新 Resolution"方向。

**④ 主要风险**：
1. 用户层撤回的意图若是"彻底放弃"而非"重新拆"，会多出一条 recommended 建议——缓解：D-151 定位当前反馈为"待处理/可关注"，可 ignore/dismiss；D-142 已裁定"处理过不等于永不推荐"。
2. 撤回已提交后重推无原子性——与 A① 同一模式：重推抛错则错误如实上抛（撤回事实不回滚），重试同一撤回入口按当前事实收敛；单配对失败不阻断其余配对（先全部尝试、末尾合并抛出）。
3. 空重跑会再次重推——由 D-142 re-offer（同 ID upsert）语义覆盖。

**⑤ 验证结果或待验证事项**：
- 已实现并经行为级测试验证（2026-10-21，见 src/tests/revocationAutoResubmit.test.ts）；方案 B 扩展实施后全量 verify 全绿（见 AGENT_STATUS §2.5）。
