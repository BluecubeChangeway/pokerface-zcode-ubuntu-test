# R3 设计报告：拆分溯源与跨批次复用（呈报用户复核，未实施）

> 依据：用户 2026-10-21 裁定（A-003，原话见 AGENT/DECISIONS-AND-ASSUMPTIONS.md）+
> D-157@Q-01-Q-09_DECISION_LEDGER.md 规则 A～E + D-158 + D-143~D-148 身份体系。
> 本报告只做设计与裁定素材，不改任何代码与语义；实施经用户批复后另轮进行。

## 一、你的裁定（设计出发点，复述确认）

1. **拆分不是把数据"切开"**，而是：一组数据源按某个条件筛选统计形成一个统计结果，再**利用条件本身**把每个结果命名为卡片；
2. 每张卡有**诞生源头**：手工筛选命名（手工卡）或拆分批量产生（拆分卡），二者地位相同；
3. 拆分卡必须记住两件事：**数据组的本源** + **拆解依据的筛选条件组**；
4. 这两点一致的两次拆分 = **相同的拆分过程**；同一张源卡使用相同拆分过程 = **复用**（不重复创建）。

## 二、系统怎么"记住"（溯源结构设计）

每次拆分执行（executionBatch）落一条**溯源记录**，与既有 WorkloadSplit 记录并行存档（不改动
D-148 批次域身份体系，不触碰撤回语义）：

```text
拆分溯源记录
├─ 本源（sourceOrigin）
│    ├─ 源结果 ID（parentWorkloadResultId）+ 其 ResultSet ID
│    ├─ 统计规则 ID（definitionId，可用时记录）        ← "工作起点是数据上传"的链条
│    └─ 执行配置 ID（executionId，可用时记录）
└─ 条件组（每个子卡一条，顺序无关——沿 D-148"顺序无业务语义"）
     ├─ 统计锚点（resultSetId + resultItemId）
     ├─ 统计维度（dimensions：科室=外科、医生=王……）
     └─ 取用上下文（targetUnitId——"渠道"的初式表达，待你确认，见问题 Q1）
```

**"相同拆分过程"的机器判定** = 本源一致（同源结果；统计规则/执行配置两侧都有时也须一致）
+ 条件组一致（锚点、维度逐项相等，不比名称不比数值——与 D-157 规则 B"完整业务身份"对齐）。

## 三、第二次拆分时系统怎么"找到并复用"（复用服务设计）

用户确认拆分（confirm_split）时，系统在真正执行前做一次**复用匹配**：

```text
拟拆分条件组 ──比对──> 既往拆分溯源（限：产物存活，revoked/已删 = 业务不存在，D-154）
   │                              │
   ├─ 子项条件完全匹配且产物存活 ──> 复用既有结果与卡片（不新建）
   ├─ 子项是新条件 ──────────────> 按需创建（D-157 规则 A）
   └─ 匹配产物已被撤回清除 ──────> 视为不存在，新建（撤回后重拆 = 新生）
```

身份体系不动：既有结果/卡片的 ID 原样引用（D-148 批次域 ID 保持不变，不跨批次改写身份）；
不产生"同内容双身份"的第二份结果——这正是 D-157 实现现状记录的最大缺口的关闭方式。

## 四、三个场景验算（用你的话说一遍）

1. **两科室同拆一张卡**：内科把"外科出院人次"按医生拆出王、李；急诊后来拖同一张源卡、
   同样按医生拆——系统识别相同（本源+条件组），**复用王、李既有卡**，不冒出第二套王、李。
2. **撤回后重拆**：你层撤回一次按医生的拆分（没在用的子卡失效、在用的保留）→
   再按同样条件拆：失效产物按"业务不存在"处理，新建；**还在用的保留子卡被匹配复用**，
   不重复——满足你"旧的衍生卡应该被新的衍生卡所替代、不能不断增长"的要求。
3. **只拆一部分**：急诊只要王，不要李——复用王的卡，李不建（按需创建）；
   内科那边的王、李照常使用，互不影响（D-157 规则 C）。

## 五、需要你确认的三个小问题（场景式）

**Q1（渠道的初式表达）**：现在系统里没有"渠道"这个对象。我的初式方案：**渠道 = 拆分时
"取用的目标科室"**。场景检验——王医生子卡同时被"内科绩效测算"和"急诊绩效测算"使用，
按这个方案**算同一个渠道**（因为都取自"内科"这次拆分），只是后续使用方不同。如果你心里
的"渠道"是**测算方案**（一个方案一个渠道），复用的判定会更严格（不同方案各拆各的）。
**你希望渠道按"科室取用"还是按"测算方案"算？**

**Q2（复用时的新名字）**：你确认拆分时若给某个子卡起了新名字，但系统发现既有拆分里已有
同条件的卡——**直接复用旧卡（忽略你这次的新名字）**，还是**照样新建一张**？
我推荐前者（复用），否则"卡片不断增长"的问题又会回来。

**Q3（复用要不要先问你）**：匹配到可复用产物时，我建议**不是静默替换**，而是在你确认
拆分的面板上写明"本次拆分将复用既有卡片：王医生（内科拆分于 10 月 1 日）、李医生……"，
**你看得见再点确认**。可以吗？还是你希望直接静默复用？

## 六、实施边界（实施轮遵守，预先声明）

- 不改封板语义：D-157 规则 A～E、D-158、D-143~D-148 全部原样；本设计是其"实施表达"；
- 溯源记录是**新增查询投影**（新建 collection，落在 local-server 的 13+1 集合上），
  不写进 WorkloadSplit 身份字段（避免身份语义漂移）；
- 复用只发生在**确认拆分执行时**（Recommendation → UserDecision 链内），不自动执行、
  不绕过用户确认（D-151/D-140 边界）；
- 溯源记录随拆分事实产生（confirm_split 持久化阶段顺带落盘），失败重试幂等（同批次
  upsert），撤回不删溯源（历史记录，匹配时按产物存活状态过滤）；
- 测试基线演进：新增复用匹配的行为级测试（三场景验算各至少一条）。
