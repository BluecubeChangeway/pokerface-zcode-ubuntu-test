# R4b 设计报告：闲时备份与恢复（呈报用户，批复后实施）

> 依据：用户存储路线裁定（A-004 阶段 2）——"未来实现服务器端备份与恢复，但不用实时备份，
> **闲时备份**即可"。本文档为实施前设计呈报；无新的业务语义变更（备份对象 = 已落盘的
> 数据集合，不涉及任何领域规则）。

## 一、用你的话说：这解决什么场景

1. **误操作恢复**：你把一整套卡和关系建错、或者批量清理过了头——一键回到昨天收工时的状态；
2. **换机迁移**：新电脑上装好系统，把旧机的备份拷过来（U 盘/网盘都行）就能原样续作；
3. **未来云端同步的载体**：你裁定的"从文件夹同步"——将来云端备份/局域网协作，同步的就是
   这份备份产物，不需要第二套机制。

## 二、设计要点（方案）

**形态**：备份 = 数据文件夹里 `backups/` 子目录下的一套**全量快照**——
`backups/2026-10-23T21-30-00/`（14 个集合 JSON 文件的完整副本 + 一张清单文件记录
备份时间与各集合行数，人可直接打开检查）。

**触发（V1）**：手动——数据来源面板加两个按钮：**"立即备份"** 和 **"从备份恢复…"**
（列表显示各备份的时间与规模，选中后需二次确认）。将来可加闲时自动备份
（服务器空闲时段/每日首次启动），V1 先不做——符合你"闲时即可、不过度建设"的原则。

**恢复语义（关键，需你点头）**：
- 恢复 = **全量替换**当前 14 个数据集合（不是合并——不猜测哪些行该留）；
- **恢复执行前，系统自动先做一次"恢复前快照"**——任何时刻你在数据文件夹里都有完整的
  "当下"，恢复错了还能再恢复回来——恢复本身永不丢数据；
- 恢复完成后界面自动重载。

**存放与边界**：
- 备份存在数据文件夹内部（`poker-face-data/backups/`）——和你的数据在一起，拷贝/同步
  整个文件夹就自然带走了备份；未来云端同步（阶段 2 后半）直接同步此目录；
- `backups/` 目录自身**不参与**备份的备份（防套娃）、也不受"清除演示数据"影响；
- 损坏防护沿用现有原则：恢复时逐文件校验 JSON，任一损坏即中止恢复、不动现有数据
  （与服务的"坏文件拒绝启动保护现场"同一条纪律）。

**技术路径**：local-server 加三个接口（POST /api/backup 创建快照、GET /api/backups 列出、
POST /api/restore 执行恢复含自动预快照）；界面在数据来源面板加按钮。全部落在服务与
面板层，**不碰领域层**——备份的是已落盘的集合文件，领域代码零改动。

## 三、实施清单（批复后一轮完成）

1. server.mjs：三个接口 + 快照复制（原子性：先写临时目录再改名）+ 清单文件；
2. LocalFolderDataService：备份/列表/恢复的适配方法（非 DataService 接口成员——
   备份是存储层能力，不进业务接口）；
3. App 数据来源面板：两个按钮 + 备份列表选择 + 二次确认 + 恢复后重载；
4. 测试：创建/列表/恢复/恢复前自动快照/损坏中止，全链行为级；
5. 浏览器实测：备份→手动改数据→恢复→数据回滚、恢复前快照存在。

**待你批复的唯一实质点**：恢复 = 全量替换 + 恢复前自动快照（第二节）——同意回"按此实施"，
或提出你想要的恢复方式（比如"只恢复部分集合"）。
